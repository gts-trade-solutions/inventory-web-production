# `/api/v1` — Shared API Contract

> The HTTP API of the shared backend. It is used by the **mobile app**, by the **web app's client-side device
> layer** (scanning, printing, live streams), and later by **external integrations**. The web console's own
> page mutations go through Server Actions, but both routes call the same services and the same domain rules,
> so behaviour is identical.
>
> **Draft — to be agreed with the mobile team in Phase 0.8, then frozen.** After that, additive changes only:
> new optional fields and new endpoints are fine, renames and removals are not. The phone ships through app
> stores, so a breaking change costs a release cycle.
>
> Architecture: [ARCHITECTURE.md](ARCHITECTURE.md) · Plan: [PROJECT_PLAN.md](PROJECT_PLAN.md) ·
> Hardware: [DEVICE_INTEGRATION.md](DEVICE_INTEGRATION.md)

## Conventions

|             |                                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Base        | `https://<host>/api/v1`                                                                                                             |
| Format      | JSON, `Content-Type: application/json`, UTF-8                                                                                       |
| Auth        | `Authorization: Bearer <access token>`, or a web session cookie for same-origin browser calls. `/auth/token` and `/health` are open |
| Time        | ISO-8601 with an explicit offset, e.g. `2026-09-17T09:31:04.512+05:30`                                                              |
| IDs         | UUID v4 strings, lowercase. **Movement and count-session ids are generated by the client.**                                         |
| Errors      | Always the envelope below, never a bare string                                                                                      |
| Idempotency | Client-generated ids are the idempotency key; retrying any write is safe                                                            |

### Error envelope

```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Only 12 units available at A-01",
    "details": { "available": 12 },
    "requestId": "req_01J8..."
  }
}
```

| HTTP                 | `code` values                                                                                                                                                                                                                    |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400                  | `VALIDATION_FAILED`, `INVALID_CURSOR`                                                                                                                                                                                            |
| 401                  | `TOKEN_EXPIRED`, `TOKEN_INVALID`                                                                                                                                                                                                 |
| 403                  | `FORBIDDEN`, `DEVICE_REVOKED`, `SITE_NOT_ALLOWED`                                                                                                                                                                                |
| 404                  | `NOT_FOUND`                                                                                                                                                                                                                      |
| 409                  | `CONFLICT`, `SESSION_ALREADY_SUBMITTED`                                                                                                                                                                                          |
| 422                  | `UNKNOWN_ITEM`, `UNKNOWN_LOCATION`, `INVALID_QUANTITY`, `INSUFFICIENT_STOCK`, `SAME_LOCATION`, `REASON_REQUIRED`, `NO_CHANGE`                                                                                                    |
| 422 _(traceability)_ | `BATCH_REQUIRED`, `UNKNOWN_BATCH`, `BATCH_EXPIRED`, `BATCH_BLOCKED`, `EXPIRY_REQUIRED`, `SERIALS_REQUIRED`, `SERIAL_COUNT_MISMATCH`, `UNKNOWN_SERIAL`, `SERIAL_NOT_AT_LOCATION`, `SERIAL_ALREADY_ISSUED`, `REASON_CODE_REQUIRED` |
| 429                  | `RATE_LIMITED`                                                                                                                                                                                                                   |
| 500                  | `INTERNAL`                                                                                                                                                                                                                       |
| 502                  | `PRINTER_UNREACHABLE`, `READER_UNREACHABLE`                                                                                                                                                                                      |

The first group of 422 codes maps one-to-one onto the mobile `MovementError` sealed interface, so the phone
renders its existing error copy with no translation layer. The traceability group is new and needs matching
copy on the mobile side.

### Mode

Every authenticated request runs in **LIVE** or **DEMO**. The mode is carried in the signed session (web) or the
signed JWT (mobile) — **never in a header, query parameter or body**, so a client cannot choose it per request
(WADR-024). Responses echo it as `X-App-Mode: LIVE|DEMO` for display and logging only. The two modes address
different databases and different device implementations; nothing else about the API differs.

## 1. Auth

### `POST /auth/token`

Exchanges credentials for a token pair bound to a device.

```json
{
  "email": "operator@example.com",
  "password": "...",
  "device": {
    "id": "d1f0...",
    "label": "Warehouse phone 3",
    "platform": "ANDROID",
    "appVersion": "1.2.0",
    "osVersion": "14"
  }
}
```

```json
{
  "accessToken": "eyJ...",
  "refreshToken": "eyJ...",
  "expiresIn": 900,
  "user": { "id": "...", "name": "Asha R", "role": "USER" },
  "sites": [{ "id": "...", "code": "WH1", "name": "Main warehouse" }],
  "defaultSiteId": "...",
  "mode": "LIVE",
  "demoAvailable": true
}
```

The request may include `"mode": "DEMO"` to sign in against the demo database. The issued token is bound to that
mode and cannot be used against the other one; switching modes requires signing in again. `demoAvailable` tells
the client whether to offer the toggle.

`role` is one of `USER`, `SUPERVISOR`, `ADMIN`. The device registers on first use and binds to the user. An
admin revoking the device invalidates both tokens; the next call returns 403 `DEVICE_REVOKED`, and the client
**must keep its unsynced outbox** and prompt for re-login rather than discarding work.

### `POST /auth/refresh`

`{ "refreshToken": "eyJ..." }` returns a new pair. Refresh tokens rotate — the old one dies immediately.
Access token 15 minutes, refresh token 30 days.

## 2. Pull — server to client

### `GET /sync/pull?since=<cursor>&siteId=<id>&limit=500`

`since` is omitted on a first full sync. The cursor is an **opaque server-issued string**: the client stores and
returns it verbatim, and must never construct or parse one.

```json
{
  "items": [
    {
      "id": "...",
      "sku": "PKG-0004",
      "name": "Packing tape 48 mm clear",
      "category": "Packaging",
      "barcode": "8901234000047",
      "unit": "rolls",
      "reorderPoint": 40,
      "trackingMode": "NONE",
      "expiryRequired": false,
      "shelfLifeDays": null,
      "nearExpiryDays": 30,
      "barcodes": [
        { "barcode": "8901234000047", "type": "EAN13", "packSize": 1, "isPrimary": true },
        { "barcode": "18901234000044", "type": "ITF14", "packSize": 24, "isPrimary": false }
      ],
      "active": true,
      "updatedAt": "2026-09-17T09:12:00+05:30"
    }
  ],
  "locations": [
    {
      "id": "...",
      "code": "A-01",
      "name": "Aisle A · Rack 01",
      "zone": "STORAGE",
      "active": true,
      "updatedAt": "..."
    }
  ],
  "batches": [
    {
      "id": "...",
      "itemId": "...",
      "batchNo": "LOT-2026-0412",
      "mfgDate": "2026-04-12",
      "expiryDate": "2027-04-12",
      "supplierRef": "SUP-8871",
      "status": "ACTIVE",
      "updatedAt": "..."
    }
  ],
  "serialUnits": [
    {
      "id": "...",
      "itemId": "...",
      "serialNo": "TLS-0015-000231",
      "batchId": null,
      "epc": "3034F4A8C0E40000000002EE",
      "status": "IN_STOCK",
      "locationId": "...",
      "updatedAt": "..."
    }
  ],
  "reasonCodes": [
    {
      "id": "...",
      "code": "DAMAGE",
      "label": "Damaged in handling",
      "appliesTo": "ADJUST",
      "requiresNote": true,
      "active": true
    }
  ],
  "stockLevels": [
    { "itemId": "...", "locationId": "...", "batchId": null, "quantity": 212, "updatedAt": "..." }
  ],
  "labelTemplates": [
    {
      "id": "...",
      "name": "Item label 100×50",
      "kind": "ITEM",
      "zplBody": "^XA...^XZ",
      "widthMm": 100,
      "heightMm": 50,
      "dpi": 203,
      "rfidEncode": false,
      "updatedAt": "..."
    }
  ],
  "settings": { "adjustmentLimit": 100, "countAutoApproveThreshold": null },
  "tombstones": [{ "entity": "ITEM", "id": "..." }],
  "nextCursor": "c_01J8...",
  "hasMore": false
}
```

- `hasMore: true` means call again immediately with `nextCursor`; the client is still catching up.
- `tombstones` cover soft-deleted and deactivated master data, so a client drops them locally.
- `stockLevels` is the server's projection. A client with unsynced movements applies its own on top —
  **the server value is not authoritative until the outbox is empty**, or stock appears to jump backwards.
- `category` is a string, matching the mobile `Item.category` field, even though the server normalises
  categories into their own table.
- **`trackingMode`** is `NONE`, `BATCH` or `SERIAL` and drives what a movement for that item must carry (§3).
  An item set to `NONE` behaves exactly as in the mobile MVP today.
- **`batches` and `serialUnits`** are only sent for items whose tracking mode needs them. `serialUnits` is the
  largest payload in the system and pages independently — a client may defer it and pull it per item on demand
  by calling `GET /serials?itemId=...`.
- `batchId` is `null` in `stockLevels` for untracked items. The server's sentinel UUID is an implementation
  detail and is never sent over the wire.

## 3. Push — client to server

### `POST /sync/push`

The outbox in `occurredAt` order, in batches of up to 200.

```json
{
  "movements": [
    {
      "id": "7f3c...",
      "itemId": "...",
      "type": "ISSUE",
      "quantity": 24,
      "fromLocationId": "...",
      "toLocationId": null,
      "batchId": "...",
      "serialUnitIds": null,
      "reasonCodeId": null,
      "note": "Line 3 replenishment",
      "reference": "WO-4471",
      "occurredAt": "2026-09-17T08:55:12.004+05:30",
      "siteId": "...",
      "deviceId": "d1f0...",
      "countSessionId": null
    }
  ]
}
```

**What a movement must carry, by the item's tracking mode:**

| `trackingMode` | Required        | Notes                                                                                                                                                                                         |
| -------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NONE`         | quantity only   | `batchId` and `serialUnitIds` must be `null`                                                                                                                                                  |
| `BATCH`        | `batchId`       | On `RECEIVE`, send `newBatch: { batchNo, mfgDate, expiryDate, supplierRef }` instead, and the server creates it. Issuing an expired or blocked batch is rejected unless site policy is `WARN` |
| `SERIAL`       | `serialUnitIds` | Exactly `quantity` entries. On `RECEIVE`, send `newSerials: [{ serialNo, epc? }]` instead. The server rejects a count mismatch — it is a bug, not a rounding difference                       |

`ADJUST` and `SCRAP` additionally require `reasonCodeId`. The server assigns `doc_no` on arrival, so an offline
movement gets its document number when it syncs; the response includes it.

Each row is judged independently, so a single bad row never blocks the batch:

```json
{
  "results": [
    { "id": "7f3c...", "status": "ACCEPTED", "docNo": "ISS-2026-000451" },
    { "id": "9a11...", "status": "DUPLICATE", "docNo": "RCV-2026-000123" },
    {
      "id": "b402...",
      "status": "FLAGGED",
      "reason": "NEGATIVE_STOCK",
      "docNo": "ISS-2026-000452",
      "details": { "itemId": "...", "locationId": "...", "resultingQuantity": -3 }
    },
    {
      "id": "d7e0...",
      "status": "FLAGGED",
      "reason": "SERIAL_CONFLICT",
      "docNo": "ISS-2026-000453",
      "details": {
        "serialUnitIds": ["..."],
        "issuedBy": "MOV-2026-000087",
        "action": "QUARANTINED"
      }
    },
    {
      "id": "c518...",
      "status": "REJECTED",
      "error": { "code": "UNKNOWN_LOCATION", "message": "Location no longer exists" }
    }
  ],
  "serverTime": "2026-09-17T09:31:04.512+05:30"
}
```

| Status      | Meaning                                                                        | What the client does                                 |
| ----------- | ------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `ACCEPTED`  | Written to the ledger and the projection                                       | Mark synced, drop from the outbox                    |
| `DUPLICATE` | This id already exists — an earlier attempt succeeded                          | Mark synced, drop from the outbox. **Not an error**  |
| `FLAGGED`   | Written, but it drove stock negative; a supervisor now owns it (WADR-007)      | Mark synced; may show an advisory                    |
| `REJECTED`  | Not written. Structurally invalid, or it references data that no longer exists | Keep for operator review; **never silently discard** |

Only `REJECTED` needs a human at the client. `FLAGGED` is deliberate policy: an offline client cannot know
another device already issued the stock, and rejecting the row would discard work already done on the floor.

**`SERIAL_CONFLICT` is the exception worth understanding.** Two devices issuing the same physical unit is not an
arithmetic disagreement — it is impossible, so one of the two operators is wrong about what they were holding.
Both movements are recorded, the later one is flagged, and the unit is quarantined pending a supervisor
decision. It is never auto-merged (WADR-020).

### `POST /movements`

Single online write, used by the web client and by integrations. Same body as one element above, same validation,
but **rejects on insufficient stock** rather than flagging, because an online caller can be told before it
commits. Returns the created movement and the affected stock levels.

## 4. Cycle counts

### `POST /counts`

`{ "id": "<client uuid>", "locationId": "...", "siteId": "...", "method": "RFID", "startedAt": "..." }`
→ `201`, status `COUNTING`.

### `POST /counts/{id}/tags`

Streams raw RFID reads into an open session, for live progress and for the audit trail. Safe to retry; reads are
de-duplicated by `(sessionId, epc)`.

```json
{ "tags": [{ "epc": "3034F4A8C0E40000000002EE", "rssi": -52, "readAt": "..." }] }
```

```json
{
  "accepted": 128,
  "duplicates": 34,
  "unknownEpcs": 2,
  "progress": { "found": 118, "missing": 4, "unexpected": 1 }
}
```

### `POST /counts/{id}/submit`

```json
{ "counted": [{ "itemId": "...", "quantity": 210 }], "submittedAt": "..." }
```

```json
{
  "sessionId": "...",
  "status": "SUBMITTED",
  "lines": [{ "itemId": "...", "expected": 212, "counted": 210, "difference": -2 }],
  "message": "Submitted for approval. No stock has changed yet."
}
```

**This differs from the current mobile MVP**, which posts COUNT adjustments on submit. The real system stores
the variance and posts nothing until approval (WADR-008), so the phone must say "submitted for approval", not
"stock updated" — a small UI change on the mobile side.

### `POST /counts/{id}/approve` · `POST /counts/{id}/reject`

Requires `SUPERVISOR` or `ADMIN`. Approval posts the COUNT movements in one transaction and returns them.
Available to both clients, so a supervisor on the floor can approve from a phone.

### `GET /counts?status=...&siteId=...`

Lists sessions, so either client can show what is awaiting approval and what was approved or rejected.

## 5. Labels and printing

One print path for both clients (WADR-014), so there is one queue and one history.

### `GET /label-templates?kind=ITEM`

Returns active templates with their ZPL bodies, dimensions and `rfidEncode` flag.

### `POST /print`

```json
{
  "id": "<client uuid>",
  "templateId": "...",
  "printerDeviceId": "...",
  "copies": 2,
  "data": { "itemId": "...", "locationId": "..." },
  "encodeRfid": true
}
```

```json
{ "jobId": "...", "status": "SENT", "zpl": "^XA...^XZ", "epcs": ["3034F4A8C0E4..."] }
```

The server renders the ZPL from the template, allocates EPCs when `encodeRfid` is set, opens a socket to the
printer, and records everything in `print_jobs`. `status` is `SENT` for fire-and-forget TCP 9100, or `CONFIRMED`
where the printer model reports back. A `502 PRINTER_UNREACHABLE` means the job is queued for retry, not lost.

**Locally attached printers** are a client-side path: the browser renders via `GET /print/render` (ZPL only, no
transmission) and sends it through Zebra Browser Print, then reports the outcome to `POST /print/{id}/result`
so the history stays complete.

### `POST /epc/allocate`

```json
{ "itemId": "...", "count": 500 }
```

```json
{
  "itemId": "...",
  "gtin13": "8901234000047",
  "serialFrom": 12000,
  "serialTo": 12499,
  "expiresAt": "2026-10-17T00:00:00+05:30"
}
```

The client encodes SGTIN-96 EPCs from its own block using the existing `Sgtin96.fromGtin13(gtin13, serial)`.
Blocks are never reissued, which is what prevents duplicate EPCs on physical tags. Clients request a new block
when their remaining serials run low, so being offline never blocks label printing.

## 6. Devices and realtime

### `GET /devices` · `POST /devices` · `PATCH /devices/{id}`

The shared device registry: scanners, readers, printers and mobile computers. Admins register network devices;
scanners and mobile computers self-register on first connection.

### `POST /devices/heartbeat`

`{ "appVersion": "1.2.0", "pendingCount": 4, "batteryPercent": 62 }` — updates `last_seen_at`, feeds the
dashboard's device-health panel and the stale-device exception list.

### `GET /stream` _(SSE)_

Server-sent events for live UI. Subscribe with `?topics=stock,counts,devices,tags&siteId=...`:

| Event               | Payload                                                       |
| ------------------- | ------------------------------------------------------------- |
| `stock.changed`     | `{ itemId, locationId, quantity }`                            |
| `movement.recorded` | the movement, plus who and which device                       |
| `count.progress`    | `{ sessionId, found, missing, unexpected }`                   |
| `tag.read`          | `{ sessionId, epc, rssi, itemId }` — live fixed-reader stream |
| `device.event`      | connection, trigger, print, error — the live event console    |
| `print.status`      | `{ jobId, status, error }`                                    |

### `GET /health`

`{ "status": "ok", "time": "...", "version": "1.4.0" }` — unauthenticated, for uptime checks.

## 7. Traceability

### `GET /batches?itemId=...&status=...&expiringBefore=...`

The batch register. `expiringBefore` drives the expiry board and the near-expiry exception list.

### `POST /batches`

Creates a batch ahead of a receipt. Usually unnecessary — a `RECEIVE` with `newBatch` creates it inline.

### `PATCH /batches/{id}` — `{ "status": "QUARANTINE", "reasonCodeId": "..." }`

Quarantine, block or release a batch. Requires `SUPERVISOR` or `ADMIN`. Quarantined stock stays on hand but
cannot be issued — the mechanism used during an investigation or a recall.

### `GET /serials?itemId=...&status=...&locationId=...&epc=...`

The serial unit register. `epc` resolves a scanned RFID tag straight to its unit, which is what makes RFID
counts unit-level rather than quantity-level.

### `GET /serials/{id}/history`

The full life of one physical unit — every movement it appears in, with document numbers, locations, operators
and devices:

```json
{
  "unit": { "id": "...", "serialNo": "TLS-0015-000231", "epc": "3034F4...", "status": "ISSUED" },
  "history": [
    { "docNo": "RCV-2026-000123", "type": "RECEIVE", "to": "RCV", "at": "...", "user": "Asha R" },
    {
      "docNo": "MOV-2026-000087",
      "type": "MOVE",
      "from": "RCV",
      "to": "A-01",
      "at": "...",
      "user": "Asha R"
    },
    { "docNo": "CNT-2026-000031", "type": "COUNT", "at": "...", "note": "Cycle count at A-01" },
    { "docNo": "ISS-2026-000451", "type": "ISSUE", "from": "A-01", "at": "...", "user": "Ravi K" }
  ]
}
```

### `GET /trace/batch/{batchId}`

The recall query: every movement of the batch, everywhere its stock currently sits, and every serial unit that
came from it. This is the question a quality incident actually asks, and it must answer in one call.

## 8. Demo mode

### `GET /demo/status`

`{ "mode": "DEMO", "seededAt": "...", "resetAvailable": true }`

### `POST /demo/reset`

Admin only, **DEMO mode only**. Drops and reseeds the demo database from the deterministic seed and returns when
complete. Refused with 403 in LIVE mode — there is no code path from this endpoint to the live database.

```json
{ "status": "ok", "seededAt": "...", "items": 50, "locations": 6, "batches": 27, "serialUnits": 84 }
```

Everything else in this contract behaves identically in both modes. That is the point: the demo exercises the
production code path, so a demo is evidence about the real system (DEMO_MODE.md §3).

## 9. Rules for both teams

1. **Cursors are opaque.** The client never builds, parses or compares one. Device clocks drift; as far as the
   protocol is concerned, the server's does not.
2. **The client clock is recorded, not trusted.** `occurredAt` comes from the client and is stored for the
   operator's timeline. `recorded_at` is server time and is what ordering and cursors use.
3. **Push before pull** in each sync cycle, so a client's own writes are reflected in what it pulls back.
4. **Never drop an unsynced movement.** Not on logout, not on a 401, not on a failed token refresh. The outbox
   is work someone physically did.
5. **Additive changes only** once frozen. New optional fields and new endpoints are fine; renaming or removing a
   field means `/v2`.
6. **Unknown fields are ignored** by both sides, so the server can add fields before the clients ship.
7. **Respect the item's tracking mode.** A client must not send a `batchId` for an untracked item, nor omit
   serials for a serial-tracked one. The server rejects both, but the client should never get there.
8. **Never invent a serial or an EPC.** Serials come from the operator, the supplier or the server; EPCs come
   from an allocated block. A locally invented identifier becomes a duplicate physical tag, which is
   unrecoverable in the field.
9. **Mode is not a client choice per request.** It is fixed when the token is issued. Do not add a mode header.
